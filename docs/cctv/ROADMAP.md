## Phase 0: วางรากฐาน (2–3 สัปดาห์)

**เป้าหมาย:** ทีมพร้อมเขียนโค้ดบนรากฐานเดียวกัน และมีอุปกรณ์จริงให้ทดสอบ

- [ ] จัดหา **ห้องแล็บ**: Dahua NVR 1 เครื่อง + กล้อง Dahua 2–4 ตัว (ควรมีกล้องที่มี AI อย่างน้อย 1 ตัว) และ switch PoE
- [ ] ขอ **เอกสาร Dahua HTTP API ฉบับทางการ** (และ NetSDK สำรองไว้) จากตัวแทนจำหน่าย
- [x] โครงสร้างโปรเจค
- [ ] Git repository + CI (lint + test): รอติดตั้ง Git
- [x] Docker Compose: PostgreSQL, Redis, MediaMTX, API, Web (ยังไม่ได้ทดสอบรันจริง)
- [x] โครง FastAPI + Alembic + ระบบ login/JWT + RBAC พื้นฐาน + audit log
- [x] โครง React + i18n ภาษาไทย + หน้า login (ยังไม่ได้ build: รอติดตั้ง Node.js)
- [x] กำหนด `DeviceDriver` interface และ `NormalizedEvent` schema
- [x] `DahuaDriver` เบื้องต้น + คำสั่ง `probe` สำหรับทดสอบกับอุปกรณ์จริง

- [x] ทดสอบกับ NVR จริง (DHI-NVR5416-16P-4KS2, firmware 2016): RTSP ใช้ไม่ได้ จึงเพิ่มช่องทาง **Dahua NetSDK**
- [x] เส้นทางภาพครบ: NVR → NetSDK → ffmpeg bridge → MediaMTX → WebRTC → เบราว์เซอร์ (ทดสอบผ่าน CLI `--publish`)
- [ ] `docker compose up` บน Linux (ยังไม่ได้ทดสอบ: เครื่องพัฒนาไม่มี Docker)
- [ ] รับเหตุการณ์ Motion จากเครื่องจริง (รอเปิด Motion Detection ช่อง 2 ที่ NVR)
- [ ] ขอเงื่อนไข license เชิงพาณิชย์ของ NetSDK จาก Dahua

**เสร็จเมื่อ:** `docker compose up` แล้วเข้าหน้าเว็บและ login ได้, ทดสอบเรียก Dahua API จากสคริปต์ได้

> **สถานะ 2026-11-23 (พักงาน):** Phase 0 เสร็จเกือบทั้งหมด งานถัดไปคือ Phase 1:
> ตัวช่วยเพิ่มอุปกรณ์ (บันทึกช่องทาง rtsp/netsdk ลงฐานข้อมูล), stream worker ที่เปิด bridge ใหม่เองเมื่อหลุด, และหน้าดูภาพสดแบบแบ่งจอ

## Phase 1: MVP ดูภาพสด (6–8 สัปดาห์)

**เป้าหมาย:** ผู้ดูแลเพิ่ม NVR ได้เอง และผู้ใช้ดูภาพสดแบบหลายช่องได้

- [ ] `DahuaDriver`: device info, รายการช่องจาก NVR, stream URL, snapshot
- [ ] Wizard เพิ่มอุปกรณ์: กรอก IP/user/pass → ตรวจสอบ → ดึงรายการกล้องอัตโนมัติ → ตั้งชื่อ/โซน
- [ ] เข้ารหัสรหัสผ่านอุปกรณ์ในฐานข้อมูล
- [ ] เชื่อม MediaMTX ผ่าน Control API: สร้าง path ต่อกล้อง (main/sub) แบบ on-demand
- [ ] หน้าภาพสด: ต้นไม้กล้อง, แบ่งจอ 1/4/9/16/25/36, drag & drop, ดับเบิลคลิกเพื่อดูเต็มจอ (สลับเป็น main stream)
- [ ] บันทึก/โหลด/แชร์ Layout, ส่งออก/นำเข้าไฟล์ Layout
- [ ] Snapshot → ดาวน์โหลดไฟล์ `.jpg`
- [ ] Health check: สถานะ online/offline ของอุปกรณ์และกล้อง

**เสร็จเมื่อ:** เพิ่ม NVR ในแล็บแล้วเห็นกล้องทุกตัว, ดู 16 ช่องพร้อมกันได้ลื่นไหล, ปิดเบราว์เซอร์แล้วเปิดใหม่ Layout ยังอยู่

---

## Phase 2: บันทึกและย้อนหลัง (6 สัปดาห์)

**เป้าหมาย:** บันทึกบนเซิร์ฟเวอร์ และดูย้อนหลังได้ทั้งจากเซิร์ฟเวอร์และ NVR

- [ ] นโยบายการบันทึกต่อกล้อง (ต่อเนื่อง/เหตุการณ์/ไม่บันทึก, main/sub) → ตั้งค่าไปที่ MediaMTX
- [ ] จัดทำดัชนีไฟล์บันทึกในฐานข้อมูล + Retention job + แจ้งเตือนเมื่อดิสก์ใกล้เต็ม
- [ ] `DahuaDriver`: ค้นหาไฟล์บันทึกใน NVR (`mediaFileFind`) + สร้าง playback URL
- [ ] หน้าย้อนหลัง: เลือกกล้อง → วันที่ → Timeline 24 ชม. → เล่น/หยุด/ความเร็ว
- [ ] เลือกแหล่งข้อมูลอัตโนมัติ (เซิร์ฟเวอร์ → NVR)
- [ ] ส่งออกคลิป `.mp4` + บันทึก audit log

**เสร็จเมื่อ:** ย้อนดูเหตุการณ์ของเมื่อวานได้ทั้งจากเซิร์ฟเวอร์และจาก NVR และส่งออกคลิปได้ภายใน 3 คลิก

---

## Phase 3: ระบบแจ้งเตือน (4–6 สัปดาห์)

**เป้าหมาย:** แจ้งเตือน Motion และ AI จากทั้งกล้องและ NVR แบบ real-time

- [ ] Device Worker: เชื่อม `eventManager.cgi?action=attach` แบบต่อเนื่อง พร้อม reconnect อัตโนมัติ
- [ ] แปลงรหัสเหตุการณ์ Dahua → `NormalizedEvent` (motion, line_crossing, intrusion, human, vehicle, face, video_loss, tamper, disk_error)
- [ ] รวมเหตุการณ์ซ้ำ (dedup) ระหว่างกล้องและ NVR
- [ ] ถ่าย snapshot ตอนเกิดเหตุ + ทำเครื่องหมายบน timeline
- [ ] กฎการแจ้งเตือน: ประเภท, กล้อง/โซน, ช่วงเวลา, ระดับความสำคัญ
- [ ] ศูนย์แจ้งเตือน: popup + เสียง, รายการพร้อมภาพ, รับทราบ/ปิดเรื่อง/หมายเหตุ, ค้นหาย้อนหลัง

**เสร็จเมื่อ:** เดินผ่านเส้นที่กล้อง AI แล้วหน้าจอแจ้งเตือนภายใน 2 วินาที พร้อมภาพ และกดดูย้อนหลังจากการแจ้งเตือนได้ทันที

---

## Phase 4: ทดสอบระบบใหญ่และนำร่อง (4 สัปดาห์) ⭐ จุดส่งมอบแรก

**เป้าหมาย:** พร้อมใช้งานจริงที่ 256 กล้อง / 10 NVR

- [ ] Load test: 256 กล้อง (ใช้กล้องจริงผสมกับ stream จำลอง), วัด CPU/RAM/แบนด์วิดท์/ดิสก์
- [ ] ปรับจูนและยืนยันสเปกฮาร์ดแวร์ และกำหนดจำนวน Recorder Node
- [ ] Hardening: HTTPS, ล็อกบัญชี, สำรองข้อมูลอัตโนมัติ, ตรวจความปลอดภัย
- [ ] ทดสอบความใช้ง่ายกับพนักงานเทศบาลจริง 3–5 คน แล้วแก้ตามผล
- [ ] คู่มือผู้ใช้ภาษาไทย + วิดีโอสอน + คู่มือติดตั้งสำหรับทีมช่าง
- [ ] ติดตั้งที่เทศบาลนำร่อง 1 แห่ง

**เสร็จเมื่อ:** ระบบทำงานต่อเนื่อง 2 สัปดาห์โดยไม่ต้องแก้ไขฉุกเฉิน และผู้ใช้ทำงานหลักได้เองโดยไม่ต้องถาม

---

## Phase 5: รองรับหลายยี่ห้อ (8–10 สัปดาห์)

- [ ] `OnvifDriver` (Profile S/G/T) + ค้นหาอุปกรณ์ในเครือข่าย (WS-Discovery): ทำก่อน เพราะใช้กับยี่ห้ออื่นได้ทันที
- [ ] `HikvisionDriver` (ISAPI + alertStream)
- [ ] `UniviewDriver` (LAPI): ต้องได้เอกสารจาก Uniview ก่อน
- [ ] ชุดทดสอบ Driver แบบเดียวกันทุกยี่ห้อ (contract tests) + ตารางความสามารถที่รองรับต่อรุ่น
- [ ] ตรวจยี่ห้ออัตโนมัติใน Wizard

---

## Phase 6: ฟีเจอร์ขั้นสูง (ต่อเนื่อง จัดลำดับตามความต้องการลูกค้า)

- PTZ (หมุน/ซูม/preset) บนหน้าภาพสด
- แผนที่ (E-Map) วางกล้องบนแผนผัง/แผนที่เมือง
- Video Wall / จอห้องควบคุมหลายจอ + Tour สลับ Layout อัตโนมัติ
- ส่งแจ้งเตือนทาง Telegram / LINE Messaging API / Email
- ดูย้อนหลังพร้อมกันหลายกล้องแบบ sync เวลา
- Mobile app หรือ PWA
- AI ฝั่งเซิร์ฟเวอร์ (เช่น อ่านป้ายทะเบียน นับคน) สำหรับกล้องที่ไม่มี AI ในตัว
- รองรับหลายสาขา/หลายเทศบาลในระบบเดียว + ระบบ License
- 2FA, เชื่อม LDAP/AD, รายงานสรุปรายเดือน

## ความเสี่ยงหลักและวิธีรับมือ

| ความเสี่ยง | ผลกระทบ | วิธีรับมือ |
|---|---|---|
| พื้นที่จัดเก็บสูงกว่างบประมาณ (main stream 30 วัน ≈ 165–330 TB) | สูง | ให้ NVR เป็นที่เก็บหลัก, เซิร์ฟเวอร์เก็บ sub-stream + เหตุการณ์, ตกลงนโยบายกับลูกค้าตั้งแต่ Phase 0 |
| Firmware Dahua แต่ละรุ่นตอบ API ไม่เหมือนกัน | กลาง | ทดสอบกับรุ่นที่ลูกค้าใช้จริง, ตรวจ capability ก่อนเรียก, ใช้ rroller/dahua เป็นแหล่งอ้างอิงกรณีพิเศษ |
| เบราว์เซอร์เล่น H.265 ไม่ได้ | กลาง | บังคับ sub-stream เป็น H.264, ถ้าจำเป็นให้ transcode เฉพาะตอนดูเต็มจอ |
| License ไลบรารี (เช่น python-amcrest เป็น GPL) | กลาง | เขียน Driver เอง ใช้ไลบรารีภายนอกเป็นแหล่งอ้างอิงเท่านั้น, ตรวจ license ของทุก dependency ใน CI |
| Uniview ไม่มีเอกสาร API สาธารณะ | กลาง | ติดต่อ Uniview ตั้งแต่ตอนนี้ และใช้ ONVIF เป็นทางสำรอง |
| ทีมขาดประสบการณ์ frontend | กลาง | จัดคนดูแล frontend เฉพาะ, ใช้ UI kit สำเร็จรูป |
| ผู้ใช้ไม่คุ้นกับระบบ | สูง | ทดสอบความใช้ง่ายตั้งแต่ Phase 1, แยกโหมดผู้ใช้/ผู้ดูแล, คู่มือภาษาไทย |

## สิ่งที่ต้องตัดสินใจหรือจัดหาตอนนี้

1. ห้องแล็บ Dahua (NVR + กล้อง AI) และเอกสาร HTTP API ทางการ
2. นโยบายการเก็บภาพ (กี่วัน, main หรือ sub stream) ซึ่งส่งผลต่อราคาฮาร์ดแวร์ที่เสนอลูกค้า
3. ผู้รับผิดชอบ frontend
4. ชื่อผลิตภัณฑ์ (ใช้ตั้งชื่อ repository และ package)
